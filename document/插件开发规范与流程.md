# 插件开发规范与流程

## 1. 功能定位
本篇用于统一说明开源版仓库中服务端模块与 Web 插件的开发边界、目录结构、注入方式、打包方式、安装方式和二开流程，帮助开发者在不污染主框架的前提下交付扩展能力。

## 2. 核心能力
- 服务端模块通过 `contracts + server` 结构挂入系统。
- 服务端生命周期由 `IServerModule` 控制，权限声明可由 `IModulePermissionProvider` 提供。
- Web 插件通过 `web/src/plugins/core` 的宿主能力完成依赖、钩子、组件和资源注入。
- 模块管理器提供上传、验证、安装、启停、打包、回滚和灰度等运维能力。

## 3. 使用场景
- 新建一个可安装、可升级的服务端业务模块。
- 为现有模块补充 Web 插件能力。
- 将模块源码或编译产物打包为可分发包。
- 在开发环境安装或调试插件，再部署到生产环境。

## 4. 使用方法
- 目录结构遵循 `src/Module/Ginkgo.Module.Xxx/contracts`、`server` 的模式。
- 服务端入口应实现 `IServerModule`，在 `Initialize` 中注册服务，在 `OnLoadAsync`、`OnUnloadAsync` 中处理生命周期。
- Web 插件应在 `web/src/plugins/installed/<plugin>/index.ts` 中导出 `Plugin` 对象，通过 `install(api)` 注册钩子和组件。
- 模块的安装、热重载、打包、卸载统一通过 `ModulesController` 与后台模块管理页完成。

## 5. 快速调用
- 服务端模块抽象：`src/Server/Ginkgo.Plugin.Abstractions/IServerModule.cs`
- 服务端权限声明：`src/Server/Ginkgo.Plugin.Abstractions/IModulePermissionProvider.cs`
- Web 插件类型：`web/src/plugins/core/types.ts`
- Web 插件管理器：`web/src/plugins/core/PluginManager.ts`
- 模块打包与安装：`src/Server/Ginkgo.Api/Modules/ModulePackageService.cs`、`ModuleInstaller.cs`

## 6. 二次开发
- 新服务端模块优先引用契约项目，不要跨模块直接硬引用实现项目。
- 新 Web 能力优先通过插件宿主扩展，不要直接把插件页面并入主框架系统页。
- 若扩展需要权限，应同步声明菜单资源、角色授权和前端按钮权限。

## 7. 关键入口
- 模块运行时：`src/Server/Ginkgo.Api/Modules`
- 模块控制器：`src/Server/Ginkgo.Api/Controllers/ModulesController.cs`
- Web 插件宿主：`web/src/plugins/core`
- 模块管理页：`web/src/views/admin/system/ModuleManager.vue`
- 插件管理页：`web/src/views/admin/system/PluginManager.vue`

## 8. 注意事项
- 插件与模块不应为单一业务需求修改主框架核心项目。
- 当前仓库默认 MySQL，涉及安装 SQL、初始化 SQL、导入脚本时应优先按 MySQL 语法组织。
- 插件代码中**禁止**出现反引号 `` `...` ``、中括号 `[...]` 包裹表名等方言字面量，以及 `UTC_TIMESTAMP()`/`GETUTCDATE()`/`sys.objects` 等方言专属字面量；统一注入 `IDatabaseDialect` 通过 `dialect.QuoteTable(...)`/`dialect.UtcNowExpr` 等抽象 API 拼装跨库 SQL。详细规则参见《[数据库方言扩展规范](./数据库方言扩展规范.md)》。
- Web 端插件页面组件应使用动态导入，不要在宿主路由注册时做静态全量导入。

## 9. Web 插件加载策略（必读）
为提升首屏速度，Web 宿主对 `web/src/plugins/installed/*` 下的插件采用**按路由路径懒加载**的装载策略，配合「始终加载（横切关注点）」白名单兜底，开发新 Web 插件时必须明确选择装载模式，否则容易出现「插件已安装、钩子未触发」的隐性故障。

### 9.1 三种装载模式
1. **按路径懒加载（默认）** —— 仅当用户访问到与插件目录段匹配的路由时才装载。例如目录名为 `tenant` 的插件，进入 `/admin/tenant/*` 才装载，进入 `/admin/dashboard` 不装载该插件代码。
2. **始终加载（横切关注点）** —— 在任意一次插件系统初始化时无条件装载，由插件在自身 `module.json` 中通过 `"loadPolicy": "always"` 字段自行声明。框架不在代码里硬编码任何具体插件名。
3. **门户共享容器兜底** —— 进入带 `meta.portalShellNeedsPlugins: true` 的静态注册路由（典型如会员中心 `/web/user*`）时，由 `router/index.ts` 的 `ensurePortalPluginsLoaded()` 触发首次门户全量装载一次门户业务插件。

### 9.2 何时必须使用 `loadPolicy: "always"`
插件注册的钩子或路由属于以下任一情形时，必须声明 `loadPolicy: "always"`：
- **HTTP 拦截类钩子**：如 `http:biz-error`（拦截后端 449/特殊业务码并弹出验证码、自动刷新等）。任何接口调用都可能命中这类钩子，包括登录请求本身。
- **静态登录页/注册页/找回密码页插槽**：如 `slot:login-actions`、`slot:admin-login-actions`。门户登录页 `/web/login` 与后台登录页 `/admin/login` 是静态注册路由，不会触发 `initPortalPluginRoutes` / `initPluginRoutes`，按路径懒加载的插件根本拿不到这些插槽。
- **顶层独立路由**：如 `portal:standalone-route` 注册的 OAuth/支付/扫码回调路由（典型 `/auth/callback/:provider`）。用户直接命中回调地址时不会经过门户路由分支，回调路由必须事先就已注册到 `vue-router`，否则白屏。
- **全局认证钩子**：如 `auth:login`、`auth:logout`，要求登录页加载时就处于已注册状态。

### 9.3 何时不应使用 `loadPolicy: "always"`
仅注册业务路由（`route:register`、`menu:register`、`portal:route-register`、`portal:user-menu` 等）的常规业务插件，必须保持默认懒加载策略，不应声明 always，否则会把首屏代价无谓拉高。

### 9.4 module.json 关键字段
始终加载型插件的 `web/src/plugins/installed/<plugin>/module.json` 必须至少包含：
```json
{
  "moduleId": "Ginkgo.Module.<后端模块 id>",
  "loadPolicy": "always",
  "loadPolicyReason": "为何必须始终加载，给运维和后续维护者看的简短解释"
}
```
说明：
- `moduleId` 必须与该插件对应的服务端 `module.json` 中的 `id` 完全一致（含大小写）。框架据此把"后端启用列表"与"前端目录名"做精准匹配，避免目录名与后端模块名不一致时被错误过滤。
- 普通业务插件不需要写 `loadPolicy` 字段，缺省即为按路径懒加载。
- 即使声明 `loadPolicy: "always"`，仍受"后端模块启用状态"约束：后端模块未启用，前端插件也不会被装载（避免装载永远没法用的钩子）。

### 9.5 自检流程
新增或调整 Web 插件钩子注册前，按下列顺序确认装载策略：
1. 钩子是否在用户**未登录、未访问业务页**时就需要被触发？是 → 必须 always。
2. 钩子是否承担**全局横切关注点**（HTTP 错误拦截、全局浮动组件、顶层独立路由）？是 → 必须 always。
3. 钩子是否承担**门户共享容器插槽**（如会员中心侧边栏 `portal:user-menu`）？是 → 不需要 always，但相应静态容器路由必须声明 `meta.portalShellNeedsPlugins: true`，参见 9.6。
4. 钩子仅在用户进入插件自身业务页面时被使用？是 → 保持默认懒加载，不要声明 always。
5. 加完 `loadPolicy: "always"` 后，进入 `/web/login`、`/admin/login` 各做一次回归，确认钩子已生效（典型回归点：449 弹验证码、登录页第三方按钮可见、OAuth 回调可正常落地）。

### 9.6 门户共享容器路由（`portalShellNeedsPlugins`）
有一类钩子既不属于「应用级横切」（不需要在登录页就装载），也不属于「插件自身业务页面」（不会随着进入插件路由而装载），它们承担的是**门户用户场景下的共享插槽**——典型例子：

- `portal:user-menu`：会员中心侧边栏聚合菜单项。
- 未来类似的「门户共享插槽」钩子（如个人中心顶部操作区、消息中心扩展卡片等）。

会员中心相关路由（`/web/user`、`/web/user/profile`、`/web/user/notifications`、`/web/user/logs`）是**静态注册**的，进入时 `vue-router` 直接命中、`router/index.ts` 中的 `initPortalPluginRoutes` 会因 `isMatchedBeforePortal === true` 而被跳过。结果就是各业务插件不装载、对应钩子从未注册、共享插槽空白。

#### 标准做法
1. **路由侧**：在所有承担「门户共享容器」的静态路由 `meta` 中显式标记 `portalShellNeedsPlugins: true`。例如 `web/src/router/web.ts` 中的 `userRoutes`：
   ```ts
   { path: 'user', name: 'web-user-center',
     component: () => import('../views/web/user/UserCenter.vue'),
     meta: { requiresAuth: true, portalShellNeedsPlugins: true } }
   ```
2. **路由守卫侧**：`router/index.ts` 的 `beforeEach` 在 `/web/*` 分支已统一处理：
   ```ts
   if (to.matched.some(m => m.meta?.portalShellNeedsPlugins)) {
     await ensurePortalPluginsLoaded()
   }
   ```
   `ensurePortalPluginsLoaded` 内部带短路缓存（`portalFullPluginsLoaded`），首次进入会员中心装载一次后续命中即可短路返回。
3. **插件侧**：业务插件正常通过 `api.addHook('portal:user-menu', ...)` 注册菜单项即可，**无需** `loadPolicy: "always"`，**无需**插件作者关心 router 兜底机制；只要会员中心容器路由继续带着 `portalShellNeedsPlugins`，钩子就能在用户进入会员中心时被正确收集。

#### 何时需要给新的静态容器加 `portalShellNeedsPlugins`
- 该容器的页面会通过 `executeHook` 同步聚合插件注入的子项，且容器路由是静态注册（不是由 `portal:route-register` 动态注入）。
- 该聚合行为的可见结果直接面向用户（缺失会让用户感知「插件没生效」）。

不要把 `portalShellNeedsPlugins` 当成「懒加载兜底」的银弹滥用：仅在确有「静态容器 + 共享插槽聚合」时使用，避免每次进入门户页都付出全量装载代价。

## 10. 接口注释（标题）规范（可选，但强烈推荐）

为了让运维人员在监控、审计、日志等横切页面上**直接看懂某条 URL 到底在做什么**，主框架提供了一项可选的接口元数据扩展：`EndpointCommentAttribute`。

> 这是一个「接口注释（标题）」特性，写的是**短标题**而不是完整接口说明。它和 .NET 内置的 `Microsoft.AspNetCore.Http.EndpointDescriptionAttribute`（OpenAPI 用）不同，命名为 `EndpointComment` 是为了避免冲突，且额外提供 `Category` 运维分类标签。

### 10.1 设计目标
1. **可选**：只是元数据，不写也能正常运行；写了之后会被资源监控、接口审计等运维页自动消费。
2. **短标题**：用一句话概括接口能力，**6–15 字最佳，最长不超过 20 字**。不要写成段落或完整接口说明。
3. **零业务耦合**：注释不参与权限、路由、参数绑定、序列化等任何业务逻辑。

### 10.2 标注方式
1. 引用 `Ginkgo.Plugin.Abstractions`（主框架与所有 server 端模块本来就引用），即可使用 `EndpointCommentAttribute`。
2. 标注在 **Action 方法** 上时表示该接口的标题；标注在 **Controller 类** 上时表示该控制器下所有未单独标注接口的兜底标题。
3. 标题**面向运维**，使用最终用户能看懂的中文业务语言（不要贴英文函数名、变量名、HTTP 细节）。**只写"是什么"，不写"怎么做"**。
4. 可选 `Category` 字段用来打标签，例如 `"只读"`、`"会写库"`、`"高危操作"`、`"后台管理"`、`"门户自助"` 等，方便运维面板分组/着色。

```csharp
// 标注在 Action 上：单条短标题
[HttpGet("customers/{id}")]
[EndpointComment("查询客户档案", Category = "只读")]
public async Task<IActionResult> GetCustomer(long id) { ... }

// 标注在 Controller 上：作为该控制器内未单独标注接口的兜底标题
[ApiController]
[Route("api/oauth")]
[EndpointComment("OAuth2 令牌端点")]
public sealed class OAuthTokenController : ControllerBase { ... }
```

**好坏对比**

| 不推荐（太长，像说明） | 推荐（短标题） |
| --- | --- |
| `颁发或刷新 access_token / id_token / refresh_token，支持三种 grant_type` | `颁发/刷新 OAuth2 令牌` |
| `获取资源看板顶部统计卡片（请求数、异常数、平均响应、内存峰值）` | `看板顶部统计卡片` |
| `修改资源监控的 CPU/内存阈值与限流参数，会作用于后续采样表现` | `更新资源监控阈值` |

### 10.3 主框架查询能力
1. 主框架 `EndpointDescriptionCatalog`（DI 单例）会扫描所有 MVC Action 上的 `[EndpointComment]`，按 **HTTP Method + 路由模板** 建立内存索引；模块热加载后自动重建。
2. 通过 `IActionDescriptorCollectionProvider` 感知模块新增/卸载，无需手动注册。
3. 暴露的查询 API（统一鉴权、需要 `Permission` 策略）：
   - `GET /api/endpoint-descriptions/resolve?method=GET&path=/api/...`：单条反查。
   - `POST /api/endpoint-descriptions/batch`：批量反查，body 为 `{ "items": [{ "method": "GET", "path": "/api/..." }] }`，返回顺序与入参一致。
4. 没有标注的接口会在响应中以 `description: null` 返回，调用方应按"有则显示、无则不显示"渲染，不要因 null 报错。

### 10.4 前端通用客户端
1. WEB 端统一封装在 `web/src/api/endpointDescription.ts`（`resolveEndpointDescription` / `resolveEndpointDescriptions` / `resolveEndpointDescriptionsCached`）。
2. `resolveEndpointDescriptionsCached` 自带进程内缓存与 inflight 合并：同一个 path 在一次会话中只请求一次，相同 path 的并发请求会共享同一个 promise，对监控类高频刷新页面非常友好。

### 10.5 写标题时的注意事项
1. **写短标题，不写长说明**：6–15 字最佳；超过 20 字就要重新审视是不是把"参数说明 / 业务流程"塞进来了。
2. **不要重复 URL 信息**（如不要写"GET /api/customers/{id} 查询客户"），只写业务含义。
3. **写操作必标**：高危/写库/支付/吊销/批量删除等接口务必加标题并打 `Category`，方便运维一眼识别。
4. 仅供运维**只读展示**：永远不要在业务代码里读取 `EndpointDescriptionCatalog` 来做权限判定、路由分发等业务决策——它只是给「人」看的元数据。
5. 标题**与代码同源**：当接口能力发生变化（如改写库语义、合并端点）时，必须同步更新标题，避免运维看到的说明与实际行为脱节。

## 11. 常见问题
- 模块包能上传不能安装：优先检查入口程序集、安装脚本、manifest 和依赖声明。
- Web 插件已注册但页面不出现：先检查插件启用状态、钩子位置和宿主路由是否正确挂接。
- Web 插件 `http:biz-error`/`slot:login-actions`/`portal:standalone-route` 钩子在登录页失效：检查该插件 `module.json` 是否声明了 `"loadPolicy": "always"`，参见上文 9.2/9.4。
- 会员中心侧边栏看不到 `portal:user-menu` 注入的插件菜单：检查会员中心容器路由 `meta` 是否带了 `portalShellNeedsPlugins: true`，参见 9.6。
