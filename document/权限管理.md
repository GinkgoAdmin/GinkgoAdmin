# 权限管理

## 1. 功能定位
权限管理负责把用户、角色、部门、菜单、按钮与 API 访问串成统一授权链路，是主框架最核心的安全与组织控制能力。

## 2. 核心能力
- 通过 `Permission` 策略对控制器执行统一授权。
- 通过 `MenusController`、`RolesController`、`UsersController`、`DepartmentsController` 维护授权对象与组织对象。
- 菜单资源既承担导航入口，也承担按钮/API 的权限映射基础。
- 角色支持权限分配、权限树和数据范围配置。
- 管理员角色在当前实现中具有特殊放行能力。

## 3. 使用场景
- 控制后台页面是否可见、按钮是否可点、接口是否可访问。
- 控制用户属于哪些角色、角色可访问哪些菜单与权限项。
- 控制角色的数据范围，影响业务数据查询边界。
- 控制导航树、我的按钮权限和菜单分组导航。

## 4. 使用方法
```mermaid
flowchart LR
    Login["用户登录"] --> Token["JWT/Claims"]
    Token --> Policy["Permission 策略"]
    Policy --> MenuMatch["按 Method + Resource 匹配菜单资源"]
    MenuMatch --> RoleGrant["校验角色是否授予该权限"]
    RoleGrant --> DataScope["按角色数据范围过滤数据"]
    DataScope --> Result["返回页面或接口结果"]
```
- 先在菜单或菜单分组中配置资源路径和方法，再把权限授予角色。
- 用户通过用户管理绑定角色，必要时再绑定部门与岗位责任。
- 角色管理页可查看权限树、当前角色权限和数据范围配置。
- Web 后台的系统页会基于这条链路展示或隐藏系统能力。

## 5. 快速调用
- 查看角色权限：`GET /api/v1/roles/{id}/permissions`
- 保存角色权限：`POST /api/v1/roles/{id}/permissions`
- 查看角色数据范围：`GET /api/v1/roles/{id}/data-scope`
- 查看我的菜单树：`GET /api/v1/menus/tree/my`
- 查看我的按钮权限：`GET /api/v1/menus/my/buttons`

## 6. 二次开发
- 新增系统能力时，应优先补菜单资源和角色授权，不要只在前端做显示隐藏。
- 插件或模块若需要声明权限，应实现 `IModulePermissionProvider`，让权限项进入系统菜单/权限体系。
- 数据范围控制应继续沿用角色维度，不要在控制器里临时硬编码用户可见范围。

## 7. 关键入口
- 授权处理：`src/Server/Ginkgo.Api/Auth/PermissionAuthorization.cs`
- JWT 与授权装配：`src/Server/Ginkgo.Api/Bootstrap/AuthenticationSetup.cs`
- 用户角色：`src/Server/Ginkgo.Api/Controllers/UsersController.cs`
- 角色权限与数据范围：`src/Server/Ginkgo.Api/Controllers/RolesController.cs`
- 菜单资源：`src/Server/Ginkgo.Api/Controllers/MenusController.cs`
- Web 页：`web/src/views/admin/system/Users.vue`、`Roles.vue`、`Menus.vue`

## 8. 注意事项
- 只在前端写 `v-permission` 不等于真正安全，后端资源与方法也必须进入菜单权限链路。
- 菜单项的资源路径和 HTTP 方法配置错误，会直接导致接口无法访问或权限失真。
- 新增系统页时，应同步考虑菜单树、按钮权限、角色授权和数据范围四个层面。

## 9. 常见问题
- 有角色但打不开接口：通常是菜单资源未配置、方法不匹配或角色权限未授予。
- 页面能看见但按钮点不了：先检查我的按钮权限接口返回，再核对按钮权限码。
- 数据看不全：优先检查角色数据范围配置，而不是先怀疑查询代码。
