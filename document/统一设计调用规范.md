# Ginkgo Framework 统一设计调用规范

> **目的**：约束开发者（含 AI 助手）在 Web 端进行业务实现时，**禁止重复造轮子**。所有可跨场景复用的能力必须从框架的统一封装出发，调用层保持简洁、一致、可维护。

本规范是 [`AGENTS.md`](../AGENTS.md) 在「统一调用」维度的详细补充，违反时优先以本规范为准修复。

---

## 0. 总则

1. **唯一入口**：每一类「可复用能力」必须有且只有一个统一入口（utility / service / 委托）。新增功能时第一步是**搜索是否已有入口**，禁止平行新建。
2. **零本地重复**：禁止在页面、组件、插件中拷贝粘贴 URL 拼接、Token 注入、鉴权拦截、日期格式化、提示弹窗等通用逻辑。
3. **后台与门户对齐**：同一业务能力在 Web 后台与 Web 前台门户上必须语义一致；命名、行为、降级策略、token 来源、错误处理须一致或显式注释偏差原因。
4. **变更必须升级公共层**：发现公共能力缺漏时，**先扩展公共层**再迁回业务层调用，不在业务层临时绕过。
5. **本规范是 Code Review 的硬门槛**：任何 PR 引入新的本地重复实现都必须先重构。

## 1. 资源 URL（图片 / 附件 / 文件预览）

### 1.1 唯一入口

| 端 | 文件 | 公开 API |
|---|---|---|
| Web | `@/web/src/utils/resourceUrl.ts` | `fetchResourceConfig()`、`getResourceConfigSync()`、`resolveResourcePath(path)`、`resolveFileUrl(file)`、`resetResourceConfig()` |

> 资源配置缓存由 OSS 等存储模块的 Web 插件在自身 `install()` 钩子中完成。**业务侧不需要也不应再去拉取或缓存资源配置。**

### 1.2 调用规则

所有需要展示/下载图片或附件的代码：

1. **绝对禁止**自行写 `getImageUrl` / `getCoverUrl` / `coverUrl` / `getPreviewUrl` 等局部函数处理 `/uploads/`、`publicBaseUrl`、`http`、`/api/files/{id}` 等分支。
2. **绝对禁止**在 Vue 模板里手写 `${baseUrl}/uploads/${url}`、`${publicBaseUrl}/${path}`、`/api/files/${id}` 等字符串拼接。
3. 拿到来自后端的：
   - **完整文件对象**（含 `url` / `storageProvider` / `id`）→ 调用 `resolveFileUrl(file)`。
   - **只有相对路径或单个字段**（如系统配置 LOGO、商品封面、截图）→ 调用 `resolveResourcePath(path)`。
4. **页面/组件首次访问前必须确保资源配置已加载**：在 `onMounted` 中 `await fetchResourceConfig().catch(() => {})` 后再加载数据。

### 1.3 已弃用模式（禁止再写）

```ts
// ❌ 禁止：重复实现
function getImageUrl(path: string): string {
  if (path.startsWith('http')) return path
  if (path.startsWith('/uploads/')) return path
  return `/api/files/${path}`
}

// ✅ 正确
import { resolveResourcePath } from '@/utils/resourceUrl'
const getImageUrl = resolveResourcePath
```

```vue
<!-- ❌ 禁止：模板里手写拼接 -->
<img :src="`/uploads/${row.coverImage}`" />

<!-- ✅ 正确 -->
<img :src="resolveResourcePath(row.coverImage)" />
```

### 1.4 上传与下载

- **上传**：走 `@/api/files.ts`。**禁止**再封装新的上传 helper。
- **下载**：永远走 `/api/v1/files/{id}/download`（服务端处理 OSS 重定向 / Content-Disposition）。

## 2. 鉴权与 HTTP 请求

### 2.1 唯一入口

| 端 | 入口 | 已处理事项 |
|---|---|---|
| Web | `@/web/src/api/http.ts`（默认导出 `http` 实例） | `/api` 前缀、后台 `auth-token` / 门户 `web_user_token` 读取、`Authorization: Bearer` 注入、401/403 提示与跳转 |

### 2.2 规则

1. **所有插件、模块、页面**对接后台 API 时**必须**复用统一 `http` 实例；禁止在插件里裸写 `fetch` / `axios.create` 处理鉴权。
2. **仅在统一入口无法直接覆盖的特例**（上传、下载、SSE、WebSocket、第三方 SDK 回调）允许定制请求；定制时必须沿用同一来源的 `token` 与 `Authorization` 头格式，并复用同一套登录失效跳转。
3. **后端**接口必须复用主框架 `[Authorize]` / 权限策略 / 用户上下文获取方式；禁止插件自建用户表登录、token 解析、权限校验。

---

## 3. 列表 / 表格 / 分页 / 搜索

- **统一组件**：`@/web/src/components/DataTable.vue`（含搜索栏、工具栏、表格区、分页区）。
- **新插件列表页必须复用 `DataTable`**，参考"我的日志"等页。除非业务方明确要求独立视觉，否则禁止另起一套。
- 操作列必须**固定在最右侧**，溢出时仅业务列横向滚动。
- 操作按钮**一行最多 5 个**，2/3/4 个时也保持单行；超过 5 个换行，需考虑 iPad 中分辨率可读性。
- `el-pagination` 的 `total` 必须 `Number(data.total) || 0`，避免 BigInt 字符串导致的渲染异常。
- `el-table-column` 主信息列使用 `min-width` 而非 `width`，确保自适应。

---

## 4. 关联对象选择（用户 / 部门 / 角色 / 客户 / 联系人 / 文件 等）

1. **可清空、可跳过**：除非业务规则明确要求必填并经用户确认，所有关联选择必须支持清空与不选择。
2. **统一选择器**：用户/部门/角色 选择器在 `@/web/src/components/` 下统一封装；文件选择走 `@/web/src/components/FileSelector.vue` 与 `ResourcePicker.vue`。
3. **禁止**让用户直接手输 ID 作为常规交互；必须提供搜索 + 选择 + 清空的体验。
4. JSON 配置界面优先使用点选 / 开关 / 单选 / 多选 / 下拉 / 远程搜索选择，尽量减少自由文本。

---

## 5. 时间 / ID / 数据库

> 与 `AGENTS.md` 第三章保持一致，此处只列调用层注意事项。

1. 后端实体与数据库统一 `DateTime.Now`（中国时区），**禁止** `DateTime.UtcNow`。
2. 雪花 ID（长整型）传到前端**必须保持字符串**。Web 端**禁止** `Number(id)` 强制转换。
3. 默认数据库 = MySQL（InnoDB）；boolean 用 `TINYINT(1)`；时间用 `DATETIME(6)`；分页 `LIMIT offset, count`。

---

## 6. 模块 / 插件之间调用

1. **跨模块调用必须走 Contracts**：
   - 需要被外部调用的服务接口/DTO 定义在 `Ginkgo.Module.XXX.Contracts`，工程**保持零第三方依赖**。
   - 业务模块仅引用目标模块的 `.Contracts.csproj`，通过依赖注入调用接口。
2. **绝对禁止**为了某个插件去修改主框架（`Ginkgo.Api`、`Ginkgo.Application`、`Ginkgo.Domain`、`Ginkgo.Infrastructure`、`Ginkgo.Plugin.Abstractions`、`Ginkgo.Shared`）。
3. **绝对禁止**在 `Ginkgo.Plugin.Abstractions` 中添加具体业务语义接口（如支付、用户）。

---

## 7. 配置文件

1. 插件**禁止**在主框架 `appsettings.json` 中寄生配置。
2. 插件配置必须放在自身 `server/config/` 下（`xxx.json.sample` 模板 + 运行时生成的 `xxx.json`），格式遵循 `groups` + `items`，由后台 UI 动态读取解析。
3. 路径解析必须走 `Ginkgo.Shared.ModuleConfigResolver`：`Resolve(Type, fileName)` / `ResolveAll(Type, fileName)` / `ResolveServerDir(Type)`，**禁止**自行拼接 `AppContext.BaseDirectory + "../config/..."`。

---

## 8. 通用规则：新增 / 修改功能 / 插件时的检查清单

> 所有 AI 助手与开发者在动手编码前必须按此清单自检。任意一项未满足都应**先扩展公共层**或调整方案，再开始实现业务代码。

### 8.1 设计前

- [ ] 是否已存在同类公共封装？（资源 URL、HTTP、鉴权、列表、选择器、配置解析…）
- [ ] 新功能是否会破坏 Web 后台 / Web 门户任一端的统一调用入口？
- [ ] 是否会触碰主框架红线（核心项目代码、ALC 白名单、抽象层）？
- [ ] 数据库设计是否符合 MySQL 约定（命名、索引、字段类型、雪花 ID）？

### 8.2 实现中

- [ ] 不复制粘贴 URL 拼接、Token、登录失效、上传下载、列表分页、选择器逻辑；统一调用既有入口。
- [ ] 不在主框架 `appsettings.json` 写插件配置；走 `ModuleConfigResolver` + `server/config/`。
- [ ] 不直接引用其他模块的实现项目；只引用其 `.Contracts`。
- [ ] 后台与门户协同功能：交互、数据语义、闭环必须一致。
- [ ] 控制台 / 报表 / 仪表盘页：必须**端到端可用**，含真实数据 + 真实快捷入口，不留花哨占位。

### 8.3 收尾前

- [ ] 全文 grep `'/uploads/'`、`'publicBaseUrl'`、`'getImageUrl'`、`'/api/files/'`、`'access_token'`、`'fetch('` 等关键字，确认没有引入新的本地重复实现。
- [ ] 注释、字段、文案均为正常 UTF-8 中文，无乱码。
- [ ] 时间字段、雪花 ID 字段、boolean 字段在前后端一致。
- [ ] 与本规范有偏差时，**在代码中以中文注释解释原因**，并在 PR 描述中点出。

---

## 9. 偏差与例外

如果业务上确实必须偏离本规范（如对接外部第三方 SDK、为兼容旧数据保留过渡逻辑），必须满足：

1. 在偏差代码上方写中文注释，说明：**为什么必须偏离 + 影响范围 + 计划何时归一**。
2. 在 PR 描述里显式点出偏差点，便于评审追踪。
3. 偏差代码不得污染公共层，仅限于该业务文件内部。

## 附录：常见反例与正例对照

| 场景 | ❌ 反例 | ✅ 正例 |
|---|---|---|
| 商品封面图 | `<img :src="'/uploads/' + item.imageUrl" />` | `<img :src="resolveResourcePath(item.imageUrl)" />` |
| 文件预览 URL | `getPreviewUrl(row) { return row.url ? '/uploads/' + row.url : '/api/files/' + row.id }` | `getPreviewUrl(row) { return resolveFileUrl({ id: row.id, url: row.url, storageProvider: row.storageProvider }) }` |
| 插件 API 调用 | `fetch('http://server/...', { headers: { Authorization: 'Bearer ' + token } })` | `import http from '@/api/http'; http.get('/xxx')` |
| 跨模块取数据 | 直接 `ProjectReference` 另一个模块的 server 工程 | 仅引用其 `.Contracts.csproj`，DI 调用接口 |
| 插件自有配置 | 写到 `Ginkgo.Api/appsettings.json` | 放到 `src/Module/Ginkgo.Module.XXX/server/config/xxx.json`，`ModuleConfigResolver.Resolve(...)` 读取 |
